# @chengchengzhao/dsh-session-manager

[中文](README.zh.md) | English

A session-management plugin for the DeepSeek Harness (DSH). It folds the formerly
standalone **dshm** web app (its own process on `127.0.0.1:8787`) **onto the DSH
port**, and adds a "Sessions" panel in Settings so it lives inside the DSH GUI.

## What it provides

| Form | Location | Notes |
| --- | --- | --- |
| Settings panel | DSH → Settings → **sessions** | Overview cards, session list, full-text search, detail view (with per-step token trend), export, archive |
| Full page | **`/dshm`** on the DSH port | The original dshm single-page app (session list / search / detail drawer / trend / export), served by the host half — port 8787 is no longer needed |

All data comes from `$DSH_HOME` and is read-only apart from one operation:

| File | Used for |
| --- | --- |
| `storages/workspace.json` | Workspace registry, session grouping, archive set |
| `storages/session_projcache.json` | Session projection: title, stats, tokens, context, permissions, goal, todos |
| `settings.yaml` | Default model and other settings |
| `sessions/*/session.jsonl.zstd` | Session logs (full-text search / trend / export) |

The only **write** is `archive` / `unarchive`, which atomically replaces
`workspace.json` while preserving all other fields. Prefer archiving while the GUI
is idle, to avoid competing writes with a running Web GUI.

## Routes

All on the DSH port (default `http://127.0.0.1:3082`):

```text
GET  /dshm                                full page (the old 8787 app)
GET  /dshm/api/overview                   overview + session table + workspace table
GET  /dshm/api/session?id=<id|prefix>      one session's detail
GET  /dshm/api/search?q=&all=&reasoning=   cross-session full-text search
GET  /dshm/api/trend?id=<id>               per-step token usage series
GET  /dshm/api/export?id=&format=md|json   export a readable transcript
POST /dshm/api/archive?id=&archived=true|false
```

### Security: loopback-only

Plugin routes registered through `ctx.webServer.register` are **not behind the DSH
web-auth gate** (measured: `GET /` returns 401 while plugin routes return 200).
All routes here run through `lib/loopback.js`, which validates **both** the socket
peer address and the `Host` header — the peer check alone cannot stop DNS rebinding
(such requests genuinely originate from localhost), and the `Host` check alone
cannot stop a real remote connection. Forged-`Host` and non-loopback-peer requests
get **403**.

## Install

```bash
# local development (link to the workspace source)
dsh plugin --profile web add link:<path-to>/dshm-plugin
# after changing code: sync the core, then restart DSH
node <tools>/dshm-plugin/sync-core.mjs
```

Before publishing, run `node sync-core.mjs` (it inlines the core from the parent
`dshm/lib` into `lib/core` so the package is self-contained), then
`npm pack --dry-run` and `npm publish --access public`.


## Performance notes

A session log is a concatenation of zstd frames — one header frame, then one frame
per appended batch. Measured: 9 sessions totalling **73,000 frames** (a single file
up to 60,000), and Node's zstd **decompresses only the first frame**, so every
frame must be decoded individually. Consequently:

- Decompression uses `promisify(zstdDecompress)` with 16-way concurrency (serial
  `await` doubles the cost in thread-pool round trips) and **never blocks the host
  event loop** — which is the precondition for running safely inside the DSH process;
- Results are cached as transcript + trend keyed on file mtime and size, so repeat
  requests cost 0 ms;
- The session-id → log-path index is built in a single directory walk instead of
  re-walking the tree per session.

Measured (9 sessions / 73k frames): search ~2.6 s cold, **6 ms** warm; trend ~3.0 s
cold, **7 ms** warm; five concurrent searches total **29 ms** (the old synchronous
implementation took 11.5 s and blocked the whole server).
